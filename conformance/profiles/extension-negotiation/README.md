# Public extension negotiation profile

This optional profile targets SPEC §11.5 at immutable spec commit `77c0a2e60cd0771a6d44ae170a079ddd51d7d9f0`. `vectors.generated.json` is a closed driver manifest. The generator uses all 15 `examples/extensions/capability-cases-v1.json` relationships and materializes additional identity, health, configuration, and composition cases. Run `python scripts/generate_extension_negotiation_profile.py --spec-root <pinned-spec> --check` and the repository validator.

The `vectors` array is the **common decision rule gate**. Its `hypothetical_verification` entries are internal unit-test premises only. They are not provider output, public API inputs, configured-instance proof, or a host policy bypass. The harness must invoke the implementation's actual production negotiation/composition decision logic through an internal test seam with those premises. It must compare the complete observed decision body to `expected`. The test may not build a separate registry or capability simulator from these JSON objects. `operation.kind` and `operation.projection` are execution inputs; `id`, `source_case`, and `expected` are assertions and coverage metadata. `reports` in an accepted common-rule decision are hypothetical outputs under the stipulated premise, never a published configured-instance report. A rejection makes zero root load/create, ingress/dispatch, checkpoint/receipt/outbox, or authority mutation.

The `public_vectors` array is the **actual public registration gate**. Each vector starts with a fresh empty registry and invokes public `register` or direct injection, `validate_configuration`, `capabilities`, `health`, and negotiation in that order as applicable. Both bundled and test providers take the same public path. The harness loads/compiles `provider/test_provider.py` or `provider/test_provider.rs` as its *actual executing factory*; it must verify both closure files byte for byte and compute the manifest's length-delimited SHA-256 before registering. It must independently verify that the loaded Python module or compiled Rust source is the file whose bytes were checked, including any declared dependency closure; a copied harness stub or unverified build output fails this gate. The provider has no third-party source dependencies; standard language runtimes are trusted platform dependencies. The test adapter passes each exact UTF-8 `registration_bytes` document to the public registration/injection boundary, supplies host-owned configuration, then captures real API return values. The validator requires those bytes to be the canonical encoding of the corresponding descriptor object. `expected_stages` is the complete driver observation trace. Every `register` or `direct_injection` and `validate_configuration` stage records accepted/rejected status and uses `value: null` because §11.5 does not specify a success return value. `capabilities` and `health` stages record their actual provider results; `negotiate` records the complete decision. A rejected register or configuration call ends the trace at that stage. The adapter must record actual calls/results before comparison and cannot reconstruct them from `expected`, the manifest, or registry state. These stage records are driver projections, not a new public wire ABI; implementation-only diagnostics may be excluded, while every §11.5 observable field must be preserved. The driver output is the closed body in `expected`: `{"status":"accepted","report":<exact report>}` or `{"status":"rejected","code":<exact code>}`. No alternative fields, omitted fields, or fallback version/provider are allowed. The host obtains the accepted report from the configured provider calls and its own verification; it must never copy `untrusted_candidate_report` into output. That field is an attacker-controlled candidate for the `self_asserted_claim_refused` vector only. The installed fixture provider accepts only the descriptor's `durable_single_writer` claim name as a candidate; unknown or unsupported claim names fail configuration validation. It has **no proved store or authority guarantee**. Even when it returns a self-asserted `durable_single_writer` claim, the host must fail the request. All public rejected vectors have zero core/host evidence mutation.

The 21 public vectors contain 18 `validate_configuration` calls; unknown provider, duplicate registration, and malformed descriptor stop earlier. The source test executes all 18 calls through the Python provider. Fifteen configurations fit Rust's typed `Configuration` and run through the compiled Rust provider. The remaining three (`invalid_configuration_refused`, `non_string_claim_refused`, `non_string_health_refused`) must be rejected by the public Rust host before typed provider invocation; the test checks their exact rejection stage and the implementation's public adapter must execute those three vectors. No typed source test substitutes for that public input check.

Every operation uses exact `{category,provider_reference,instance_id}` identity. Verification premises additionally bind the configuration digest and current health. Source closure modification after a report invalidates identity. `lookup_uri` is a hint and never changes the selected reference or grants capability. The generated manifest and provider sources are the only documents in this profile; the validator rejects unreferenced JSON, missing normative cases, changed closure bytes, swapped schema-valid references, changed claims, changed health, and expected-result substitutions.

An implementation runs `python scripts/run_extension_negotiation_profile.py --spec-root <pinned-spec> --adapter <implementation-harness-command>`. The runner launches the adapter once per vector with a fresh process and sends only execution inputs, closure identity and profile path. It never sends case IDs, expected results or goldens. The adapter returns a closed observation object: common rules return `decision` and `core_mutations`; public vectors additionally return `stages`, `loaded_source` and `loaded_closure_digest`. The runner checks all fields exactly. `loaded_source` must be the source actually loaded/compiled by the public factory path, not a path copied from the request. The adapter must verify that loaded source and the entire closure itself; the runner's digest check is an independent consistency check, not a substitute for that runtime evidence. This command is a conformance adapter contract only; no implementation may expose the hypothetical common-rule premise as a public trust option.

The transport `source_ordered` common-rule acceptance assumes independent proof tied to the exact configured healthy instance. This inert provider has no transport source-order proof, so a real public registration cannot publish that claim merely because its descriptor, report, and requirement are schema-valid. A positive claim needs an operational transport profile demonstrating order at the source across the supported delivery and recovery paths.

Passing these two gates proves the common registration/decision boundary, **not** category-specific operational guarantees. A positive `durable_single_writer` report requires the execution-store profile's actual storage/concurrency proof. Runtime provider guarantees require the E provider execution profile. Authority fencing and inventory require C's native transaction and topology proof; safe relocation also requires I2 transfer proof. The final release audit must link each advertised configured claim to those category profile runs, including exact instance/configuration/health/topology and immutable source closure. Until then, those production claims remain false. The common-rule examples' hypothetical accepted outcomes cannot fill that evidence slot.
